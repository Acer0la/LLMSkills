# ArchSave

## 强制启动检查

在回答或编辑任何代码、审查、架构、调试、项目规则或其他重要工作之前：

读取或修改文件时使用 UTF-8 编码。

1. 如果这是当前工作区的首个代码任务、审查或其他重要任务，或工作区工作记忆不可用，先阅读本 Skill。
2. 如果 `./workArchitecture/` 存在，读取其中所有 Markdown 文件。
3. 将这些架构记录作为后续工作的有效上下文。
4. 如果该目录不存在，除非之后确实需要保存架构文档，否则继续处理而不创建目录。

## 1. 架构文档工作流

- 使用本 Skill 收集项目背景，并保存可供后续开发使用的持久架构文档。
- 文档聚焦于项目结构、框架选择、开发工作流、重要文件和维护说明。
- 架构文档使用中文记录。
- 保留项目总体建设策略，将其组织为主要目标步骤，并进一步细分为小目标工作流，以便随时中断和继续。
- 保存架构文档时，如有助于后续继续或交接，应自动纳入相关后续工作思路。
- 除非用户指定其他位置，否则将文档保存在当前工作目录下的独立文件夹中。

## 2. 用户提供项目信息并明确提出“Organize the Work Architecture”或“整理工作架构”时

- 阅读项目文档并理解项目框架。简言之，全面收集项目背景；随后检查并整理本地目录中的网站结构等信息。
- （如果用户有明确要求“编写文档”）最后编写一份便于后续开发该网站的技术文档，包含网站及相关开源项目的重要信息。

## 3. 用户提出“Summarize Today's Work”或“简述今天工作”时

- 用Git对比本地文件和github云端（本地云端记录）的修改内容，（只）根据Git对比的新增的内容和你的记忆，整理两份更新记录列表：（并且按功能分类排序，格式为“- 大项目(换行)(缩进)- 1.小项目”）
第一份：给程序员看的，用列表标标出入口和修改点。精简一点，git提交用。
第二份：给内部开发组看的，需要用列表标出功能的使用方法和更新内容，以及使用入口。
对开发组的公告要精简一点，可以忽略具体的修改点，但要描述清楚如何使用及功能（不用写出之前已经写出的功能描述，只写使用的功能修改在哪即可）。
